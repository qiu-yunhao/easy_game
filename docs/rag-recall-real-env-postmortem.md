# RAG 回忆系统真实环境测试复盘：两个检索缺陷的发现与修复

> 复盘日期：2026-08-17
> 背景：回忆栈（DataAccess 多库抽象层 + build_recall_stack 工厂 + web_demo 接线）完成组装、全部单元测试通过后，首次接入真实环境（真实 Postgres + 真实 bge 嵌入模型）做端到端验证。本次验证暴露了两个单元测试未能覆盖的检索缺陷，均已定位并修复。本文档记录事件全过程，供复盘。

---

## 一、事件概述

单元测试全绿（组装完成时 262 个测试通过）并不等于系统在真实环境可用。当我们第一次用真实的 Postgres 向量库和真实的 bge（BAAI/bge-small-zh-v1.5，本地中文嵌入模型）跑一条完整的「索引两幕剧情 → 自然语言查询回忆」链路时，结果与预期严重不符：

- 第一次运行：两条查询**全部无命中**（返回空结果）。
- 修复第一个缺陷后：两条查询都能命中，但**都命中同一幕，且语义完全对不上**——问「酒馆冲突」却返回了「山巅论剑」那一幕，两条查询的相关性得分还完全相同。

这两个现象背后是两个独立的缺陷，都出在检索链路的过滤与排序环节，都被单元测试用「理想化的测试数据」掩盖了，只有在真实数据的量纲下才会暴露。

---

## 二、缺陷一：文档类型过滤失效（doc_type filter miss）

### 现象

端到端脚本索引两幕后做自然语言查询，`RecallService.query_recall`（回忆查询服务的查询入口）返回空列表，两条查询无一命中。

### 分析过程

回忆查询采用两阶段设计：先用整幕摘要（scene_summary，粗粒度文档）做**粗召回**（coarse retrieval，即先定位「哪几幕相关」），再在命中的幕内用行动片段（act_chunk，细粒度文档）做**细召回**（fine retrieval，取具体片段）。无命中意味着第一阶段粗召回就返回了空。

为定位问题，我绕过服务层，逐层直接探查向量库：

1. **向量库无过滤直查**：用查询向量直接检索，能查到文档，余弦相似度得分 0.5995，说明数据确实写进去了、向量检索本身正常。
2. **带过滤条件检索**：加上粗召回用的过滤条件 `{user_id, player_id, doc_type: "scene_summary"}` 后，命中数变成 0。

问题锁定在过滤条件上。对比过滤条件的三个键与文档的实际存储结构，发现关键差异：`user_id`（用户标识）、`player_id`（玩家标识）这些业务字段存放在文档的 `metadata`（元数据，以 JSONB 列存储）里，而 `doc_type`（文档类型）是数据库表的一个**独立顶层列**（top-level column），并不在 metadata 里。

### 归因

向量库 `PgVectorStore`（pgvector 向量存储）和稀疏检索器 `PgTrgmSparseSearch`（基于 pg_trgm 三元组的稀疏检索）的过滤实现，对传入的**所有**过滤键都一视同仁地按 `meta ->> key`（从 JSONB 元数据列按键取值）来匹配。因此 `doc_type` 这个键被翻译成了 `meta ->> 'doc_type'`——而元数据里根本没有这个键，该表达式恒为 NULL，等值比较恒不成立。

结果：只要过滤条件里带了 `doc_type`，查询就必然返回空。而粗召回和细召回**每次都会带 `doc_type`** 来区分整幕摘要与行动片段，所以整条查询链路必然无命中。这是一个「过滤条件把自己过滤空了」的缺陷。

### 为何单元测试没抓到

向量库原有的过滤测试只验证了 metadata 里的键（如 `player_id`），恰好都是走 `meta ->> key` 的正确路径，从未测试过 `doc_type` 这个顶层列。缺陷正好落在测试覆盖的空隙里。

### 修改方案

在两个检索器的过滤逻辑里区分「顶层列」与「元数据键」：当过滤键是 `doc_type` 时，按顶层列做等值比较（`doc_type 列 = 值`）；其余键仍按 JSONB 元数据取值比较。两个检索器（向量库、稀疏检索）共用同一张表、同样的列结构，因此同步修改。

### 结果

补上一条专门针对 `doc_type` 顶层列过滤的测试（先红后绿）。修复后端到端脚本从「全部无命中」变为「能命中」，粗召回恢复正常。至此第一个缺陷解决，但立刻暴露出第二个。

## 三、缺陷二：重排因子量纲失衡（rerank factor scale imbalance）

### 现象

过滤修好后，两条本应命中不同幕的查询，结果都命中了同一幕（「山巅论剑」），且两条查询返回的相关性得分完全相同，都是 3.0098。查询「酒馆冲突」返回「山巅论剑」，语义完全错位。

### 分析过程

得分 3.0098 这个数字本身就不合理——它由三因子重排（three-factor rerank）产出，而三因子加权后的合理得分不该超过 1 左右。我把这个得分按重排公式拆开：

重排的总分 = `0.6 × relevance（相关性）+ 0.2 × recency（新近度）+ 0.2 × importance（重要度）`。

代入实际的因子取值：
- `relevance`（相关性）来自 RRF（Reciprocal Rank Fusion，倒数排名融合）分数，量级约为 `1 / (60 + 排名)`，即 **0.016 左右**；
- `recency`（新近度）当时直接取「该幕结束时的回合数」原始值，如 **2 或 12**；
- `importance`（重要度）直接取原始重要度评分，取值范围 **0 到 5**。

于是 `0.6 × 0.016 + 0.2 × 12 + 0.2 × 3 = 0.0098 + 2.4 + 0.6 = 3.0098`，与观测到的得分分毫不差。诊断由此坐实。

### 归因

三个因子的**量纲（scale，即数值范围）完全不在一个数量级**：相关性是 0.016 级别的小数，新近度是几到几十的整数，重要度是 0 到 5 的评分。它们未经归一化就直接加权相加，导致：

- 相关性对总分的贡献只有约 0.01，几乎可以忽略；
- 新近度和重要度的贡献高达数量级为 1 的值，完全主导了排序。

其后果是：排序实际上只取决于「哪一幕更靠后、更重要」，而与「查询问的是什么」几乎无关。恰好「山巅论剑」那一幕回合数更大（更新近）、重要度更高，于是无论查询什么，它都排第一。两条查询得分相同，正是因为排序已经与查询内容脱钩，只由那一幕固定的新近度和重要度决定。

### 为何单元测试没抓到

重排的原有测试传入的因子值本身就已经是归一化好的 0 到 1 之间的理想数据，三者量纲一致，自然测不出量纲失衡的问题。真实环境里因子取的是各自的原始量纲，问题才显现。这与缺陷一同源——都是「理想化测试数据掩盖了真实量纲下的缺陷」。

### 修改方案

与用户确认后，采用**候选集内 min-max 归一化**（in-candidate-set min-max normalization）：在每一次重排时，对当前候选集里的三个因子分别做 min-max 归一化，把各自的取值线性映射到 0 到 1 区间，再加权求和。这样三个因子进入加权时处于同一量纲，权重（0.6 / 0.2 / 0.2）才能真正体现设计意图。

同时处理退化边界：当某因子在候选集内所有取值都相等（例如候选集只有一个文档，max 等于 min）时，归一化会出现除零。此时统一将该因子归一化为常数 1.0——含义是「该因子在这批候选里无从区分优劣」，让它对排序不产生倾向，而非崩溃。原始因子值仍保留在 `factors`（分项因子记录）里，便于调试与结果透明化。

### 结果

补上两条测试：一条用真实量纲的数据验证「语义最相关的文档不再被量纲更大的重要度、新近度淹没」，一条验证「单候选归一化不除零」（先红后绿）。修复后重跑端到端脚本，两条查询各自命中正确的幕，语义完全对上，排序缺陷解决。

## 四、两个缺陷的共性与启示

这两个缺陷表面上一个在「过滤」、一个在「排序」，看似无关，但根因高度一致，都指向同一个薄弱点：

**单元测试使用的是经过理想化的数据，而真实环境使用的是带原始结构、原始量纲的数据。** 缺陷一里，测试只用了元数据键、没用顶层列；缺陷二里，测试只用了归一化好的因子、没用原始量纲的因子。两处都是「测试数据比真实数据更规整」，于是缺陷都藏在了测试覆盖不到的地方，直到真实环境才暴露。

由此得到的启示是明确的：

- **对存储结构敏感的逻辑**（如过滤要区分顶层列与元数据键），测试数据必须覆盖每一种结构形态，不能只挑最顺手的那一种。
- **对数值量纲敏感的逻辑**（如多因子加权），测试必须用贴近真实量纲的数据，理想化的归一化数据会掩盖量纲失衡这类问题。
- **端到端的真实环境验证不可省略**。这两个缺陷都能通过一条完整的真实链路在几分钟内暴露，却能穿过 262 个单元测试而不被发现。单元测试保证的是「每个零件按测试假设工作」，真实环境验证保证的是「零件在真实数据下组装起来仍然工作」，两者不能互相替代。
